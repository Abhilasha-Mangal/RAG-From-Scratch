Module 0

Why Do We Need RAG?
Google Exists — So What?

Large Language Models (LLMs) are incredibly capable — but they have two critical flaws that RAG directly solves.

🧠

Problem 1 — Knowledge Cutoff

GPT-4 was trained on data up to April 2023. Ask it about a drug approved in 2024, a company's latest earnings, or yesterday's news — it simply doesn't know. It will either say "I don't know" or worse — make something up.

🎭

Problem 2 — Hallucination

LLMs generate text by predicting the next most-probable token. When they don't know an answer, they confidently invent one. A medical chatbot that makes up drug dosages, a legal assistant that cites fake court cases — this is catastrophic.

💡 "But Google Already Searches the Web — Why Build RAG?"

🔍 Google Search

Returns a list of URLs. You read 10 pages. You piece together an answer yourself. No reasoning, no synthesis, no private data.

🤖 Raw LLM

Has general knowledge but no access to your company's internal docs, patient records, codebases, or anything private.

✅ RAG System

Searches your private knowledge base, retrieves the exact relevant chunks, feeds them to an LLM that reasons and answers in natural language — citing sources.

📦 Phase 1: Indexing (One-Time)

1.Load all documents with Docling
2.Split into overlapping chunks
3.Embed every chunk → float vector
4.Store in vector database (persisted)

✅ Done once. Re-run only when documents change.

⚡ Phase 2: Querying (Per Request)

1.User asks a question
2.Embed the question (same model)
3.ANN search → top-k similar chunks
4.Build prompt with chunks as context
5.LLM generates grounded answer

⚡ Happens in ~1-3 seconds per query.

Every Box Maps to a Folder and a Command

Each stage in the repo is a standalone script you can run on its own, then the pipeline in 08_full_pipeline/ ties them together.

Module 1
01

Document
Loading

IBM Docling extracts richly structured text from PDFs — preserving tables, headings, lists, and page numbers.

Why Docling over PyPDF? Docling understands document structure, not just raw text. It extracts tables as Markdown tables, preserves heading hierarchy, and handles scanned PDFs via OCR.
Output format: Markdown — clean, structured, perfect for downstream chunking.
Supported inputs: PDF, DOCX, PPTX, XLSX, HTML, Images, URLs.
pip install docling — that's all. No server, no API key.
01_document_loading/loader.py
# IBM Docling — richly structured PDF extraction from docling.document_converter import DocumentConverter from docling.datamodel.pipeline_options import PdfPipelineOptions class DoclingLoader: def __init__(self, ocr=False): opts = PdfPipelineOptions() opts.do_ocr = ocr opts.do_table_structure = True self._conv = DocumentConverter() def load_file(self, path): result = self._conv.convert(str(path)) # Export as Markdown — tables, headings preserved content = result.document.export_to_markdown() return Document( content=content, source=str(path), metadata={"pages": result.document.num_pages} ) # Usage — run from terminal: loader = DoclingLoader(ocr=False) doc = loader.load_file("data/raw/deep_learning.pdf") print(doc.content[:500]) # First 500 chars of Markdown

Plain Text Extraction vs. Docling

The same page of a PDF, extracted two ways. Flat extraction loses the heading and scrambles table cells; Docling keeps the structure as Markdown, so chunking and retrieval work on meaningful units.

Module 2
02

Text
Chunking

Embedding models have a max token limit. We must split documents into small, meaningful pieces.

Too large chunks → the context is noisy, LLM gets confused, precision drops.
Too small chunks → meaning is lost, no context around each fact.
Sweet spot: 256–512 tokens with 10–15% overlap.
Recommended: Recursive — tries paragraph → sentence → word splits in order.
02_chunking/chunker.py
# Recursive chunker — best default strategy class RecursiveChunker: SEPS = ["\n\n", "\n", ". ", " ", ""] def split(self, text, chunk_size=512, overlap=64): # Try each separator, recurse if chunk still too big parts = self._recursive_split(text, self.SEPS) return self._merge_with_overlap(parts, chunk_size, overlap)

Same Text, Four Ways to Cut It

Every strategy splits the same six sentences. Notice where the boundaries land: fixed-size cuts through sentences, recursive respects paragraphs, semantic follows meaning.

Module 3
03

Embeddings
Text → Vectors

An embedding converts text into a list of numbers (a vector) where similar meaning = similar direction.

Intuition: "dog" and "puppy" produce very close vectors. "dog" and "quantum physics" produce distant vectors.
Similarity measure: Cosine similarity — angle between two vectors. 1.0 = identical, 0 = unrelated, -1 = opposite.
Default model: all-MiniLM-L6-v2 — 384 dimensions, 90MB, runs on CPU in milliseconds.

Write Once, Query Many Times — and Swap the Backend

Indexing stores each chunk with its vector and metadata. At question time the query is embedded by the same model and the database returns the top-k nearest chunks. Only the box in the middle changes between ChromaDB and Redis.

🧠 Quick Check — Why is HNSW faster than brute-force search?
✅ Correct! HNSW builds a multi-layer graph. At the top layer it takes large "jumps" towards the query, then descends to finer layers for precision — like a geographic zoom. This gives logarithmic complexity vs. linear brute-force.
Module 5
05

Retrieval
Finding the Right Context

Not all retrieval strategies are equal. The right strategy depends on your query type and data.

top-k similarity: Fast. Returns the k most similar chunks. Simple, works well for most cases.
MMR (λ=0.7): Balances relevance AND diversity. Avoids returning 5 chunks that say the same thing.
Hybrid (BM25 + semantic): Best of both worlds. Keyword matching for exact terms + semantic search for meaning. Uses RRF fusion.
ReRank: Stage 1 fast retrieval → Stage 2 slow CrossEncoder rescoring. Most accurate, used in production.
05_retrieval/retriever.py
# Switch strategy from config.yaml retriever = build_retriever(cfg) hits = retriever.search( query, strategy="hybrid", # similarity | mmr | hybrid | rerank top_k=5 )

Four Retrieval Strategies, Side by Side

Same query, same ten chunks. Large dots are what each strategy returns. The bars show the trade-off between speed, accuracy and diversity.

Vector + Keyword = Reciprocal Rank Fusion

Vector search understands meaning but can miss exact names, IDs and acronyms. BM25 does the opposite. Hybrid runs both and merges the two ranked lists.

StrategyHow it worksUse when
SimilarityTop-k nearest vectorsDefault; quick baseline
MMRBalance relevance and diversityChunks look near-duplicate
HybridVector + BM25 merged by RRFNames, codes, acronyms in queries

Module 6
06

Prompt
Engineering

The prompt is the bridge between retrieved chunks and the LLM. Get this wrong and even perfect retrieval fails.

Tell the model to ONLY use context. Without this instruction, it will blend context with hallucinated "knowledge".
Number your sources so the model can cite [1], [2], [3].
Handle "I don't know" explicitly — tell the model to say so if the answer isn't in context.
Token budget: Keep context <3000 tokens to leave room for the answer.
06_prompting/prompt_builder.py — Numbered Template
# The Numbered Context Template (recommended default) SYSTEM: You are a helpful and accurate assistant. Answer ONLY using the context below. Do not use prior knowledge. If the answer is not in the context, say "I don't have enough info." Always cite sources as [1], [2], etc. USER: CONTEXT: [1] (Source: deep_learning.pdf, p.12) {{ chunk_1 }} [2] (Source: transformers.pdf, p.4) {{ chunk_2 }} QUESTION: {{ user_question }} ANSWER:
TemplateBest ForToken Use
NumberedGeneral Q&A, citationsMedium
XML tagsClaude-style modelsMedium
Chain-of-ThoughtComplex reasoningHigh
ConciseChatbots, speedLow

How the Prompt Is Assembled

Four blocks, in a fixed order. The instruction block is what stops hallucination; the order of context blocks matters because LLMs under-use the middle of long prompts.

Lost in the Middle

Put the best chunk first or last. Evidence in the middle of a long prompt is often ignored.

Token Budget

Context window minus question minus answer space. Drop the lowest-ranked chunks when over budget.

Prompt Injection

Documents can contain hostile text. Delimit the context and tell the model it is data, not instructions.

RAGAS scores your pipeline on 4 dimensions. Each is 0–1 (higher = better).

Faithfulness0.87

Are the retrieved chunks actually relevant to the question?

Did retrieval find all necessary information to answer?

Module 10

Advanced Techniques

Once the basic pipeline works, these push quality significantly higher.

🎯

HyDE

Hypothetical Document Embeddings. Ask the LLM to write a hypothetical answer, embed that, then search. Works because answers and source passages are closer in embedding space than questions and passages.

Query → LLM → Hypothetical Doc → Embed → Search → Real Results → Final Answer
🔁

Query Expansion

Ask the LLM to rewrite the query 3 different ways. Retrieve for all variants. Fuse results with RRF. Dramatically improves recall for ambiguous or short queries.

1 query → 3 variants → 3×retrieval → RRF fusion → top-k
🗜️

Contextual Compression

After retrieving chunks, ask the LLM to extract only the sentences relevant to the query. Removes noise from context, reduces tokens, improves faithfulness.

chunk(500 words) → compress → relevant(50 words)
🕸️

GraphRAG

Extract entities and relationships as a knowledge graph. Multi-hop queries traverse the graph — "Who worked with Einstein at Princeton?" requires connecting 3 nodes.

Tools: Microsoft GraphRAG, LlamaIndex KG, Neo4j
🤖

Agentic RAG

The LLM decides when to retrieve, what to search for, and whether to retrieve again. Uses tool-calling to iteratively gather information for complex, multi-step questions.

Tools: LangGraph, AutoGen, CrewAI, LlamaIndex
🧩

RAPTOR / Hierarchical

Cluster chunks, summarize each cluster, embed the summaries. Build a tree of abstractions. Query at multiple levels — great for long documents and thematic questions.

Chunks → clusters → summaries → tree → multi-level search

Which Fix for Which Failure?

Advanced RAG is not "use everything". Diagnose the failure first, then add exactly one technique. Each one costs extra latency or extra LLM calls.

HyDE

Cost: +1 LLM call. Best for: questions that look nothing like the document wording.

Query Expansion

Cost: +1 LLM call, N searches. Best for: broad questions and recall problems.

Compression

Cost: +1 call per chunk. Best for: small context windows and noisy PDFs.
